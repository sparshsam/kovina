## 1. Authority

### This document owns

- OpenAudit's purpose, architecture, and behavioral rules.
- Audit categories — what areas are checked and what they verify.
- Standards manifest loading and audit scope determination.
- All check definitions for repository structure, website, platform, accessibility, icon, localization, data/storage, security/privacy, performance, documentation, and release readiness.
- Scoring model, severity definitions (pass/warn/fail).

It coordinates with [TESTING_STANDARD.md](../process/TESTING_STANDARD.md) for automated test results and [RELEASE_PROCESS.md](../process/RELEASE_PROCESS.md) for release readiness.

## 2. Philosophy

OpenAudit is not a linter. It is a **compliance verifier** that checks a project against the canonical Kovina standards. It does not make up rules — it reads them from the standards library. Every check is traceable to a specific standard and section.

Audits are not punishments. They are diagnostics. A project that fails an audit is not a bad project — it is a project with known gaps that can be addressed. The audit report is the starting point for improvement, not a final judgment.

OpenAudit is designed for three audiences:

1. **Developers** — to self-check before opening a pull request.
2. **CI pipelines** — to block non-compliant changes from merging.
3. **Maintainers** — to assess ecosystem health across all Kovina projects.

## 3. OpenAudit Purpose

### What OpenAudit Does

| Function | Description |
|---|---|
| **Verify project structure** | Check that the repository follows PROJECT_STRUCTURE_STANDARD |
| **Verify standards compliance** | Check the project against every applicable standard |
| **Generate compliance reports** | Produce human-readable and machine-readable audit reports |
| **Score compliance** | Calculate a compliance score per category and overall |
| **Suggest remediation** | Provide specific, actionable steps for each failed check |
| **Integrate with CI** | Run audits as part of the CI pipeline and block non-compliant merges |
| **Hand off to manual QA** | Identify checks that require human judgment and produce QA checklist |

### What OpenAudit Does Not Do

| Function | Not OpenAudit's Responsibility |
|---|---|
| Write code to fix compliance gaps | OpenAudit diagnoses; agents fix |
| Generate new standards | Standards are maintained in the kovina repository |
| Test application logic | [TESTING_STANDARD.md](../process/TESTING_STANDARD.md) covers functional testing |
| Deploy or build the project | CI/CD handles build and deploy |
| Replace human judgment | Manual QA is required for some checks |

## 5. Standards Manifest Loading

### Loading Process

OpenAudit loads the project's standards context from `.kovina/standards.json`:

```
1. Read .kovina/standards.json
2. Validate the JSON schema
3. Determine which standards are applicable (status ≠ "not_applicable")
4. Fetch the referenced standards version (local cache or remote)
5. Parse each standard's rules for check generation
6. Schedule checks by category
```

### Manifest Resolution

| Scenario | Behavior |
|---|---|
| `.kovina/standards.json` exists | OpenAudit uses the pinned version |
| `.kovina/standards.json` does not exist | OpenAudit warns that the project was not scaffolded by OpenForge and runs with heuristics only |
| Standards fetch fails | OpenAudit uses the last cached version or fails gracefully |

### Applicability

| Rule | Rationale |
|---|---|
| A standard with `status: "not_applicable"` is skipped | The project does not require this standard |
| A standard with `status: "compliant"` is re-verified | Status may have changed since generation |
| A standard with `status: "pending"` is verified | Pending standards need checking |
| Unknown standards in the manifest are ignored | Forward compatibility |

## 8. Platform Checks

### Checks Against Platform Standards

OpenAudit determines which platform standards apply based on the project's `platforms` field in `.kovina/project.json`.

|---|---|---|
| **Web** | Static export or server config, `_headers`/`_redirects` (Cloudflare), CORS, CSP headers | Fail |

| **macOS** | .app bundle, notarization eligibility, sandbox entitlements, universal binary | Fail |
| **iOS** | Xcode project, signing, Info.plist, App Store Connect metadata, capability entitlements | Fail |
| **Android** | Gradle build, AAB/APK, adaptive icons, AndroidManifest.xml permissions, minSdk | Fail |

### Platform Check Rules

| Rule | Rationale |
|---|---|
| Only platforms declared in `.kovina/project.json` are checked | Honored scope |
| Platform checks that cannot be run statically are flagged for manual QA | Human judgment required |

## 17. Scoring Model

### Category Score

Each category (Repository Structure, Accessibility, etc.) receives:

| Component | Calculation |
|---|---|
| **Total Checks** | Count of all checks in the category |
| **Passed** | Count of checks that passed |
| **Warnings** | Count of checks that produced warnings |
| **Failed** | Count of checks that failed |
| **Manual** | Count of checks that require manual verification |
| **Category Score** | `(passed + manual) / total * 100%` |

### Overall Score

| Component | Calculation |
|---|---|
| **Overall Score** | Average of all category scores (each weighted equally) |
| **Bare Minimum** | All Fail-severity checks pass |
| **Ready for Release** | All Fail checks pass, no new Warnings introduced since last release |

### Scoring Rules

| Rule | Rationale |
|---|---|
| Manual checks are counted as "passed" for scoring (they are not failures until proven otherwise) | Humans must manually confirm or override |
| A single category at 0% sets overall to 0% | There are no compliance gaps that can be ignored |
| The score is advisory — the pass/warn/fail details are actionable | The number alone doesn't tell you what to fix |

## 18. Pass / Warn / Fail Severity

| Severity | Meaning | CI Action |
|---|---|---|
| **Pass** | The check passed. No action required. | None |
| **Warn** | The check identified a concern that should be addressed but is not blocking. | Warning in CI output. Does not block merge. |
| **Fail** | The check failed a required standard. Must be resolved before release. | Blocks merge in CI. Prevents release. |
| **Manual** | The check cannot be automated. A human must verify. | Flagged in the QA handoff report. Does not block release — but unresolved manual checks are flagged at release. |

### Severity Overrides

| Scenario | Rule |
|---|---|
| A Warn check becomes a Fail if there are 5+ Warnings in the same category | Warning accumulation degrades to failure |
| A Manual check is treated as Fail if the project is past beta stage | Manual checks must be verified before stable release |
| Severity can be escalated by project configuration | The project can tighten requirements |

## 20. Remediation Suggestions

### Requirement

Every failed check includes a remediation suggestion:

| Field | Content |
|---|---|
| **Check** | Brief description of the check |
| **Status** | Fail or Warn |
| **Source** | Standard and section that defines the rule |
| **Finding** | Specific file or configuration that failed |
| **Suggestion** | Actionable step to resolve the failure |
| **Effort** | Rough estimate (minutes, hours) |

### Remediation Format

```
## ❌ Images must have alt text
- **Source:** ACCESSIBILITY_STANDARD §10
- **Finding:** 3 images in `src/components/Header.tsx` missing `alt` attribute
- **Suggestion:** Add descriptive `alt` text to each image. For the logo, use `alt="OpenReader logo"`. For decorative elements, use `alt=""`.
- **Effort:** 5 minutes
```

## 21. CI Integration

### CI Behavior

| Trigger | Action |
|---|---|
| Pull request opened | Run OpenAudit on the feature branch |
| Pull request updated | Re-run OpenAudit on updated branch |
| Push to `main` | Run full OpenAudit + generate report artifact |
| Release tag created | Run OpenAudit with release-level severity (all Manual checks become Fail) |
| Scheduled (nightly) | Run OpenAudit across all active projects for ecosystem health dashboard |

### CI Rules

| Rule | Rationale |
|---|---|
| CI must pass all Fail-severity checks before merge | No non-compliant code enters main |
| CI warnings do not block merge but are reported | Visibility without blocking |
| CI produces a machine-readable audit report as a build artifact | Traceability |
| CI caches the standards library between runs | Speed |
| CI can skip specific checks via `.audit-ignore` file with documented justification | Escape hatch with accountability |

## 22. Manual QA Handoff

### When Manual QA Is Required

| Scenario | Reason |
|---|---|
| Accessibility screen reader and keyboard navigation tests | Cannot be fully automated |
| Visual design checks (layout, spacing, color harmony) | Subjective |
| Real-device platform testing (orientation, gestures, hardware) | Simulators are not sufficient |
| Privacy policy accuracy review | Legal compliance |
| Export/import round-trip test with real user data | Data integrity |
| Performance testing on low-end devices | Simulator cannot replicate |
| Content accuracy review | Human judgment |
| Localization quality review (translation accuracy, cultural appropriateness) | Human judgment |

### QA Handoff Format

OpenAudit produces a QA checklist:

```markdown
## Manual QA Checklist — openreader v0.1.0

### Accessibility
- [ ] Navigate entire app using only keyboard (no mouse)
- [ ] Test with VoiceOver (iOS/macOS), TalkBack (Android), NVDA (web)
- [ ] Verify all custom controls announce correct roles and states
- [ ] Test with 200% zoom — no clipping or overlap

### Visual Design
- [ ] Review all screens in dark mode
- [ ] Review all screens in light mode
- [ ] Verify spacing consistency per DESIGN_PLAYBOOK
- [ ] Verify icon alignment and sizing

### Platform
- [ ] Test on a physical device (not simulator)
- [ ] Test orientation change
- [ ] Test interruption handling (call, notification)
- [ ] Test offline, then reconnect

### Data
- [ ] Export real data, verify all fields present
- [ ] Re-import the export and verify round-trip
- [ ] Delete an item, wait 30 days (or test soft-delete expiration)
```

## 23. Prohibited Audit Behavior

| Pattern | Why It Is Prohibited |
|---|---|
| **Inventing rules not in the standards** | OpenAudit verifies against canonical standards only |
| **Hardcoding check logic that duplicates standard content** | Checks must read from the standard, not duplicate it |
| **Reporting failures without a remediation suggestion** | Every failure must be actionable |
| **Silently skipping checks** | All skipped checks must be documented with reason |
| **Modifying project files during audit** | Audits are read-only |
| **Sending audit results to external services without user consent** | Privacy boundary |
| **Failing a check that requires manual verification without flagging it as Manual** | Honest severity classification |
| **Ignoring the standards manifest version** | Must audit against the version the project declares |
| **Reporting the same failure multiple times in different categories** | Deduplication |
| **Blocking merge for a Warn-severity check without project configuration** | Warnings are not blocking by default |

## 25. Agent Checklist

Before an AI agent declares OpenAudit work complete:

### Configuration

- [ ] `.kovina/standards.json` is loaded and parsed correctly.
- [ ] Only applicable standards (not "not_applicable") are checked.
- [ ] The correct standards version is used.

### Coverage

- [ ] All 12 audit categories have checks implemented.
- [ ] Each check traces to a specific standard and section.
- [ ] Manual checks are identified and separated from automated checks.
- [ ] No check invents rules not present in the standards.

### Accuracy

- [ ] Scoring model weights categories equally.
- [ ] Fail checks correctly block CI (where configured).
- [ ] Warn checks do not block CI by default.
- [ ] Manual checks are scored as passed (pending human verification).

### Reports

- [ ] Human-readable report is generated with categories, scores, and details.
- [ ] Machine-readable report is generated as valid JSON.
- [ ] Every failure includes a remediation suggestion.
- [ ] Manual QA checklist is generated and comprehensive.

### Integrity

- [ ] Audit is read-only — no project files are modified.
- [ ] Audit results are not sent to external services without consent.
- [ ] Deduplication prevents repeated failures across categories.

### CI

- [ ] CI integration blocks merge on Fail-severity checks.
- [ ] CI reports Warn-severity checks without blocking.
- [ ] CI produces an audit report as a build artifact.
